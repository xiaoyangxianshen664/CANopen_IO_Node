# COB-ID 与 PDO 映射草案

COB的全称是Communication Object，中文通常翻译为：通信对象

因此COB-ID = Communication Object Identifier：中文是：通信对象标识符

### 1：阶段 0 已确认基线：

Node-ID=1（合法节点范围 1..127），

500 kbit/s（APB1=45 MHz 时 Prescaler=6、BS1=11TQ、BS2=3TQ、SJW=1TQ，采样点 80%），

11-bit 经典 CAN 数据帧，

DLC<=8；不接受扩展帧、RTR 或 CAN FD。



### 2：预定义连接集

| 服务 | CAN-ID 公式 | Node-ID=1 | 节点方向 | DLC |
|---|---|---|---|---|
| NMT | 0x000 | 0x000 | STM32接收 | 2 |
| EMCY | 0x080+Node_ID | 0x081 | STM32发送 | 8 |
| TPDO1 | 0x180+Node_ID | 0x181 | STM32发送 | 1 |
| RPDO1 | 0x200+Node_ID | 0x201 | STM32接收 | 1 |
| TPDO2 | 0x280+Node_ID | 0x281 | STM32发送 | 4 |
| SDO 请求 | 0x600+Node_ID | 0x601 | STM32接收 | 8 |
| SDO 响应 | 0x580+Node_ID | 0x581 | STM32发送 | 8 |
| Boot-up/Heartbeat | 0x700+Node_ID | 0x701 | STM32发送 | 1 |

NMT 的目标地址在 byte1，0 表示广播；节点自身不能取地址 0。无关 COB-ID 丢弃。CAN CRC/ACK 由控制器处理，应用不另加 Modbus CRC。





注意区分总线 CAN-ID 与对象字典中的 32 位 COB-ID 参数：节点1的 0x1800:01=0x40000181、0x1801:01=0x40000281；bit30=1 禁止 RTR，bit31=0 表示 PDO 有效，bit29=0 使用标准帧。总线上仍使用 0x181/0x281，不把标志位作为 CAN-ID 发送。RPDO1 参数为 0x201。下文报文中的编号均指总线 CAN-ID。

### 3：固定 PDO 布局

0x6000 = Index，主索引
0x01   = Sub-index，子索引

在我们项目中

Index = 0x6000：表示数字输入这一组对象
Sub-index = 0x01：表示该组中的第 1 个对象
完整对象地址 = 0x6000:01：数字输入数据

| PDO | 对象 | 映射值 | 载荷与触发 |
|---|---|---|---|
| RPDO1 | 0x6200:01，8 bit | 0x62000108 | byte0 为 DO1..4；高 4 bit 非零时整帧拒绝并计数 |
| TPDO1 | 0x6000:01，8 bit | 0x60000108 | byte0 为 DI1..4；高 4 bit 为 0；输入变化触发 |
| TPDO2 | 0x6401:01 / :02，各 16 bit | 0x64010110 / 0x64010210 | byte0..1 为 AI1，byte2..3 为 AI2；小端；事件周期默认 0，变化触发由 0x6423 控制 |

已确认采用 4 DI / 4 DO / 2 AI；DI/DO 为低 4 位按位打包，AI 对象为 INTEGER16，原始 ADC 0..4095 乘 8 后保存为 0..32760。

PDO 只在 Operational 收发和应用。进入 Operational 先发布一次当前输入；退出时清除待发 PDO。被拒绝的 RPDO 不回复 SDO abort，不改变输出。数字量在线上传输的是逻辑状态，GPIO 高低电平由 BSP 根据板卡极性转换。

第一版固定映射、固定 COB-ID、不实现 RPDO2、SYNC 和动态重映射。TPDO 定时与抑制行为见对象字典草案。





# 解析

## 一：先看整个系统在干什么

你的项目可以理解成：

```c
              CAN 总线
                  │
        ┌─────────┴─────────┐
        │                   │
     CANopen主站          STM32F429
                         Node-ID = 1
                              │
                   ┌──────────┼──────────┐
                   │          │          │
                  4 DI       4 DO       2 AI
```

STM32 这个节点：

- 采集 **4 路数字输入 DI**
- 控制 **4 路数字输出 DO**
- 采集 **2 路模拟输入 AI**
- 对外提供 CANopen 通信
- Node-ID 默认配置为 `1`（核心支持 1..127）

所以主站可以通过 CAN 总线：

```
读取/配置参数     → SDO
控制输出          → RPDO
获取输入          ← TPDO
监控节点状态      ← Heartbeat
获取严重故障      ← EMCY
控制节点状态      → NMT
```

这就是整个阶段 0 的骨架。





## 二：第一部分：CAN 总线本身怎么通信

### 1：规定Node-ID = 1 

你规定：

```c
Node-ID = 1
CAN Baudrate = 500 kbit/s
11-bit 标准帧
Classic CAN
DLC <= 8
```

这些属于底层 CAN 通信规则。

1. Node-ID = 1 （当前我们STM32从机的ID）

CANopen 给每个节点分配一个：

```
Node-ID
```

合法范围：

```
1 ~ 127
```

你的 STM32：

```
Node-ID = 1
```

因此很多 CANopen COB-ID 都可以通过：

```
基础 COB-ID + Node-ID
```

计算出来。

例如 EMCY：

```
0x080 + Node-ID
= 0x080 + 1
= 0x081
```

所以：

```
STM32 → 主站
EMCY = 0x081
```



### 2：补充

CANopen 是一个多节点总线系统，可以挂载多个节点。

例如：

```
CAN 总线
├── CANopen 主站 / CAN 分析仪
├── Node-ID = 1：STM32 智能 I/O 节点
├── Node-ID = 2：温度采集节点
├── Node-ID = 3：电机控制节点
└── Node-ID = 4：其他 I/O 节点
```

每个 CANopen 节点都有唯一的 `Node-ID`，通常范围是：

```
1～127
```

我们的 STM32 只是其中一个节点：

```
STM32 Node-ID = 1
```

它对应的 COB-ID 就是：

```
TPDO1：0x181
RPDO1：0x201
SDO 请求：0x601
SDO 响应：0x581
Heartbeat：0x701
```

如果另一个节点的 `Node-ID = 2`，它的对应 ID 就会变成：

```
TPDO1：0x182
RPDO1：0x202
SDO 请求：0x602
SDO 响应：0x582
Heartbeat：0x702
```

这样不同节点的报文不会混淆。

需要区分：

```
CAN 总线：所有节点共享的物理通信线路
CANopen 网络：运行 CANopen 协议的多个节点
Node-ID：每个节点的逻辑地址
```

在完整 CANopen 系统中，通常有：

```
一个主站
多个从站/设备节点
```

但 CAN 总线本身是多主结构，多个设备理论上都可以主动发送报文。项目 2 中，我们先把企业级 CAN 分析仪当作主站工具，把 STM32 Node-ID=1 作为被测试节点。





## 三：为什么会有这么多 COB-ID？

这是理解 CANopen 最关键的一步。

对于采用预定义连接集的通信对象，最终 COB-ID 通常由基础值加 Node-ID 得到；NMT 是例外，固定使用 0x000，目标 Node-ID 放在数据 byte1 中。

预定义连接集的基础 CAN-ID 按通信服务区分，例如 TPDO1、RPDO1、SDO；不是按电压、电流等物理量分类。

节点Node-ID：CANopen 网络：运行 CANopen 协议的多个节点 ，我们目前只挂载了一个stm32，节点ID分配了 Node-ID=1

```c
基础 COB-ID + Node-ID
          ↓
最终 COB-ID
          ↓
对应的 CAN-ID
```

| 通信对象  | 基础值 | Node-ID | 总线 CAN-ID |
| --------- | ------ | ------- | -------------------- |
| TPDO1     | 0x180  | 1       | 0x181                |
| RPDO1     | 0x200  | 1       | 0x201                |
| TPDO2     | 0x280  | 1       | 0x281                |
| SDO 请求  | 0x600  | 1       | 0x601                |
| Heartbeat | 0x700  | 1       | 0x701                |



CANopen 规定：不同的 CAN-ID，代表不同类型的通信对象。

所以你这里实际上是在给不同业务“分配频道”。

比如：

```
0x000 → NMT
0x081 → EMCY
0x181 → TPDO1
0x201 → RPDO1
0x281 → TPDO2
0x601 → SDO请求
0x581 → SDO响应
0x701 → Heartbeat
```

因此你可以把它想象成：

```
CAN 总线
│
├── 0x000  NMT
├── 0x081  EMCY
├── 0x181  TPDO1
├── 0x201  RPDO1
├── 0x281  TPDO2
├── 0x601  SDO
├── 0x581  SDO
└── 0x701  Heartbeat
```

收到 CAN 帧之后，第一件事情就是看 CAN-ID。





## 四：为什么 SDO 是 0x601 / 0x581？

这里正好可以联系你刚刚已经理解的 SDO。

你的节点：

```
Node-ID = 1
```

CANopen 规定：

```
SDO Request  = 0x600 + Node-ID
SDO Response = 0x580 + Node-ID
```

所以：

```
主站 → STM32
0x600 + 1 = 0x601

STM32 → 主站
0x580 + 1 = 0x581
```

也就是：

```
主站
 │
 │ SDO request
 │ CAN ID 0x601
 ▼
STM32
 │
 │ SDO response
 │ CAN ID 0x581
 ▼
主站
```

SDO主要干：

> “我要访问对象字典里的某个对象。”

例如：

```
读取 0x1017:00
```

或者：

```
修改某个配置参数
```





## 五、PDO 就是另一套思路

你现在已经开始理解 PDO 了。

PDO 不主要负责：

> “我要访问对象字典里的某个对象。”

而是：

> “现场过程数据直接高速传输。”

例如你的：

```
TPDO1 = 0x181
```

里面固定规定：

```
byte0 = DI1~DI4
```

那么 STM32 检测到输入变化：

```
DI1 = 1
DI2 = 0
DI3 = 1
DI4 = 0
```

就可以打包成：

```
00000101
```

然后直接发送：

```
CAN ID = 0x181
DATA[0] = 0x05
```

主站看到：

```
0x181  05
```

直接知道：

```
DI1 = 1
DI2 = 0
DI3 = 1
DI4 = 0
```

**主站不需要先发 SDO 读取请求；PDO 服务仍按固定映射从对象字典取得数据。**

这就是 PDO 的核心价值。



### 1：TPDO1 是干什么的？

你的定义：

```
TPDO1
CAN ID：0x181
方向 = STM32 → 主站
DLC = 1
```

映射：

```
0x6000:01
8 bit
```

具体规定：

```
byte0
┌────┬────┬────┬────┬────┬────┬────┬────┐
│ 7  │ 6  │ 5  │ 4  │ 3  │ 2  │ 1  │ 0  │
├────┴────┴────┴────┼────┼────┼────┼────┤
│       必须为 0     │DI4 │DI3 │DI2 │DI1 │
└────────────────────┴────┴────┴────┴────┘
```

也就是说：

```
bit0 = DI1
bit1 = DI2
bit2 = DI3
bit3 = DI4
bit4~7 = 0
```

例如：

```
DI4 DI3 DI2 DI1
 0   1   0   1
```

就是：

```
0000 0101
```

即：

```
0x05
```



### 2：0x6000:01是什么

`0x6000:01` 是 CANopen 对象字典中的一个对象地址：

```
0x6000 = Index，主索引
0x01   = Sub-index，子索引
```

在我们的项目中：

```
0x6000：数字输入这一组对象
0x6000:01：数字输入数据
```

它保存 4 路 DI 状态：

```
bit0 = DI1
bit1 = DI2
bit2 = DI3
bit3 = DI4
bit4~bit7 = 0
```

所以：

```
0x6000:01 = 0x05
```

表示：

```
DI1=1，DI2=0，DI3=1，DI4=0
```

这里的 `0x05` 是对象当前的**数据值**，不是对象地址。

------





### 3：DLC 是什么

DLC 的英文全称是：

```
Data Length Code
```

中文叫：

```
数据长度码
```

DLC 表示当前 CAN 报文中有几个有效数据字节。

经典 CAN 一帧最多携带 8 个数据字节：

```
DLC = 0：没有数据
DLC = 1：1 个数据字节
DLC = 2：2 个数据字节
...
DLC = 8：8 个数据字节
```





### 4：DLC=1 是什么意思

在我们的 TPDO1 中：

```
CAN-ID = 0x181
DLC = 1
Data[0] = 0x05
```

意思是：

> 这条 CAN 报文只有 1 个有效数据字节。

完整表示：

```
CAN ID：0x181
数据长度：1 字节
数据内容：05
```

这个 1 字节对应：

```
0x6000:01
```

因为 `0x6000:01` 使用 `UNSIGNED8`，正好占 1 字节。

对比 TPDO2：

```
TPDO2
CAN-ID = 0x281
DLC = 4
```

因为：

```
AI1：2 字节
AI2：2 字节
总共：4 字节
```

所以：

```
DLC = 4
```

最简单记忆：

```
0x6000:01：对象地址
0x05：对象数据值
DLC：这条 CAN 报文有几个数据字节
DLC=1：报文只携带 1 个数据字节
```





## 六：为什么 TPDO1 要“输入变化触发”？

因为 DI 属于典型的实时过程数据。

比如：

```
DI1 一直是 0
```

如果每 1 ms 都发送：

```
0x181 00
0x181 00
0x181 00
0x181 00
...
```

其实是在浪费 CAN 总线。

所以你的设计是：

```
DI没有变化
    ↓
不发送

DI发生变化
    ↓
立即发送 TPDO1
```

这就是：

> **事件触发型 PDO**

例如：

```
原来：
DI = 0000

DI2 变成 1

现在：
DI = 0010

STM32立即发送：

ID   DATA
181  02
```

这非常适合数字输入。上述例子以 Operational、未启用周期触发为前提；进入 Operational 的首次发布仍须执行。





## 七：RPDO1 正好反过来

你的：

```
RPDO1
COB-ID = 0x201
方向 = 主站 → STM32
DLC = 1
```

它对应：

```
0x6200:01
```

作用就是：

> **主站直接给 STM32 下发 4 路数字输出状态。**

例如：

```
主站发送：

CAN ID = 0x201
DATA[0] = 0x05
```

STM32解析：

```
bit0 → DO1 = 1
bit1 → DO2 = 0
bit2 → DO3 = 1
bit3 → DO4 = 0
```

然后：

```c
DO1 → GPIO
DO2 → GPIO
DO3 → GPIO
DO4 → GPIO
```

按位解析：

```
bit0 = 1 → DO1 开
bit1 = 0 → DO2 关
bit2 = 1 → DO3 开
bit3 = 0 → DO4 关
```

然后应用层把输出状态交给 BSP：

```
RPDO1 接收
    ↓
PDO 模块解析 DATA[0]
    ↓
更新对象 0x6200:01
    ↓
应用层处理输出命令
    ↓
BSP 控制 PB0、PB1、PB2、PB3
    ↓
LED1、LED3 亮，LED2、LED4 灭
```

这里的分层很重要：

```
PDO 层：只负责解析 CANopen 报文
对象字典：保存 0x6200:01 的输出值
应用层：决定如何执行输出
BSP 层：真正操作 GPIO
```

所以 `0x6200:01` 本身不是 GPIO，也不是 LED，而是：

> **CANopen 对象字典中表示 4 路数字输出状态的一个 UNSIGNED8 对象。**



## 八：为什么高 4 bit 非零就拒绝？

RPDO1 的 `DATA[0]` 是一个字节，但我们只定义低 4 位有效：

```
bit0 → DO1
bit1 → DO2
bit2 → DO3
bit3 → DO4
bit4~bit7 → 保留，必须为 0
```

因此：

```
0x05 = 0000 0101
```

合法：

```
DO1=1，DO2=0，DO3=1，DO4=0
```

而：

```
0x85 = 1000 0101
```

高 4 位不是 0，属于非法 RPDO 数据。

处理流程：

```
收到 CAN-ID 0x201
    ↓
检查 DLC 是否为 1
    ↓
检查 DATA[0] 的高 4 位是否为 0
    ↓
非法：丢弃整帧，DO 保持原状态
合法：更新 0x6200:01，并控制 GPIO
```

这里“不回复 SDO abort”是因为 RPDO 是实时过程数据，没有对应的请求—响应机制。它不像 SDO 那样能返回错误响应。

这项约束的意义是：

- 避免未定义位被误解释
- 发现主站配置错误
- 防止异常数据直接改变输出
- 让协议行为可预测

还需要额外记住：这只是协议层合法性检查。即使数据合法，节点仍然必须先处于 `Operational` 状态，RPDO 才执行；如果处于 `Pre-operational` 或 `Stopped`，也应忽略该 RPDO。



## 九：TPDO2：专门传两个模拟量

你的：

```
TPDO2
CAN-ID = 0x281
DLC = 4
```

里面：

```
byte0~1 → AI1
byte2~3 → AI2
```

而且是：

> **小端序**

例如：

```
原始 ADC1 = 582 → AI1 对象值 = 4656 = 0x1230
原始 ADC2 = 343 → AI2 对象值 = 2744 = 0x0AB8
```

那么 CAN 数据：

```
30 12 B8 0A
```

也就是：

```c
byte0 = AI1低8位
byte1 = AI1高8位

byte2 = AI2低8位
byte3 = AI2高8位
```



因为这是 **Modbus 和 CANopen 两套协议的数据编码规则不同**。

项目 1 的 Modbus RTU 规定：

```
16 位寄存器按大端传输
高字节在前，低字节在后
```

例如数值：

```
0x1234
```

Modbus 传输：

```
12 34
```

而 CANopen CiA 301 对常用数值对象通常采用**小端字节序**：

```
低字节在前，高字节在后
```

同一个数值：

```
0x1234
```

CANopen 传输：

```
34 12
```

所以我们的 TPDO2：

```
byte0~1：AI1
byte2~3：AI2
```

如果：

```
原始 ADC1 = 1846 → AI1 = 14768 = 0x39B0
原始 ADC2 = 2896 → AI2 = 23168 = 0x5A80
```

实际数据是：

```
B0 39 80 5A
```

解析方式：

```
ai1 = data[0] | ((uint16_t)data[1] << 8);
ai2 = data[2] | ((uint16_t)data[3] << 8);
```

原因是 CANopen 的对象字典、SDO 和 PDO 对数据类型有自己的编码约定，不能直接沿用项目 1 的 Modbus 大端规则。

但这里有一个重要原则：

```
项目 1：Modbus 层使用大端
项目 2：CANopen 层使用小端
```

这不会影响 STM32 内部变量的数值。比如：

```
uint16_t ai1 = 1830;
```

原始变量仍然是 `1830`；本项目先在更新对象时乘 8 得到 `14640`，再把对象值按小端排列。量程编码与字节序是两个步骤。

此外，PDO 映射值：

```
0x64010110
```

本身是“对象索引 + 子索引 + 位长度”的描述值，不是 AI 数据本身。真正发送 AI 数据时，才按小端排列。

所以以后项目 2 不要写“沿用项目 1 的大端”，而应在协议层统一封装：

```
co_put_u16_le()
co_get_u16_le()
```

这样 SDO 和 PDO 的字节序就不会混乱。





## 十：为什么 12 位 ADC 使用 INTEGER16？

原始 ADC 输入仍为 0..4095。对象 0x6401:01/02 使用 2 字节 INTEGER16，本项目采用单极性正值左对齐：

```text
bit15 = 0（正号）
bit14..3 = 12 位 ADC 原始数据
bit2..0 = 0
对象值 = 原始 ADC × 8
4095 → 32760 = 0x7FF8 → 小端 F8 7F
```

不是把原始值原样放入低 12 位，也不能左移 4 位使符号位变成 1。类型、编码和两字节长度是不同概念。

## 十一：TPDO2 怎样配置成 100 ms？

两组事件定时器默认均为 0（关闭周期触发）。需要 TPDO2 每 100 ms 发送时，先在 Pre-operational 写入 0x1801:05=100，再进入 Operational。0x1800:05 同样可配置。

- TPDO1：DI 变化触发；未实现可选掩码对象时采用其默认行为。
- TPDO2：0x6423:00 为 BOOLEAN，默认 0，关闭 AI 变化触发；写 1 后允许变化触发。它不控制 ADC 采集，也不是 MCU 中断开关。
- 事件定时器独立于 0x6423；默认 0 不等于禁用整个 PDO。
- 类型 255 的 TPDO 在进入 Operational 时先发送一次当前值；后续按变化/周期条件发送。
- 两组抑制时间 0x1800:03、0x1801:03 固定为 0/const。本版不提供禁用 PDO 后修改抑制时间的配置流程。

以上行为在阶段6实现和测试。

## 十二：NMT 是干什么的？

这个非常重要，因为你规定：

> PDO 只在 Operational 收发。

所以谁负责让节点进入 Operational？

就是：

```
NMT
```

你的 NMT：

```
CAN-ID = 0x000
DLC = 2
```

例如：

```
01 01
```

可以理解为：

```
命令 = 0x01（Start，进入 Operational）
目标节点 = 1
```

目标节点：

```
byte1 = 1
```

表示：

> 给 Node-ID 1 发命令。

如果：

```
byte1 = 0
```

表示：

> 广播给所有节点。

因此：

```
0x000
 │
 ├── byte0：NMT命令
 └── byte1：目标Node-ID
```

这也是为什么你特别规定：

```
0 = 广播
1~127 = 单节点
```

而 STM32 自己不能配置成：

```c
Node-ID = 0
```





## 十三、Heartbeat 是干什么的？

你的：

```
Heartbeat COB-ID = 0x701
```

因为：

```
0x700 + Node-ID
= 0x701
```

STM32 会定期告诉主站：

> **“我这个节点还活着。”**

例如：

```
0x701  05
```

其中 `05` 表示当前 CANopen NMT 状态为 Operational。

所以主站可以通过：

```
0x701
```

判断：

```
节点还活着吗？
当前处于什么状态？
```

它和 TPDO 完全不是一回事：

```
TPDO
→ 汇报过程数据

Heartbeat
→ 汇报节点自身状态/存活情况
```



## 十四、EMCY 是什么？

你的：

```
EMCY = 0x081
DLC = 8
STM32 → 主站
```

它用于：

> **设备出现错误或规定的警告时主动报告。**

比如：

```
严重故障
   ↓
STM32
   ↓
发送 EMCY
   ↓
0x081
```

它和普通诊断数据不一样。

未来可结合的系统诊断信息包括：

```
health
fault count
SD error
watchdog/reset cause
```

以后这些系统状态可以和 CANopen 的错误机制结合。另据冻结基线，0x6423=FALSE 时进入 Operational 需发送 0x0080 警告，且不因此退出 Operational；由阶段8/9落实。

可以简单理解：

```
Heartbeat
→ “我还活着”

EMCY
→ “我出严重问题了！”
```





## 十五、为什么 CAN CRC 不需要你自己处理？

这是因为你现在是在：

```
CANopen
   ↓
CAN控制器
```

CAN 本身已经提供：

- CRC
- ACK
- 位填充
- 错误检测
- 自动重发等底层机制

STM32 的 CAN 外设负责这些事情。

所以你的应用代码不应该再像 Modbus RTU 那样：

```
数据
+
CRC16
```

你以前的 Modbus：

```
01 03 00 00 00 0A CRC
```

需要应用层自己算 CRC。

CANopen：

```
CAN ID + DATA
```

CAN 控制器负责 CAN 帧本身的 CRC。

所以你这里明确写：

> 应用不另加 Modbus CRC。

这是非常正确的项目边界。





## 十六、最后一个特别重要的东西：Operational

你的设计实际上把 CANopen 节点分成了几个状态。

最核心的是：

```
Pre-operational
        │
        │ NMT Start
        ▼
Operational
```

在你的项目里：



### 1：Pre-operational

可以：

```
SDO
Heartbeat
NMT
```

但：

```
PDO ❌
```



### 2：Operational

可以：

```
SDO
PDO
Heartbeat
NMT
EMCY
```

其中 PDO 才真正开始工作。

所以你规定：

> **进入 Operational 先发布一次当前输入。**

非常合理。

例如节点刚进入 Operational：

```
DI当前状态 = 1010
```

即使刚刚没有发生输入变化，也先发送一次：

```
0x181  0x0A
```

让主站立即知道当前状态。

然后后面才继续：

```
DI变化
 ↓
TPDO1
```



## 十七、你这份阶段 0 最终可以浓缩成这一张图

```c
 				CANopen Node
                   STM32F429
                  Node-ID = 1
                       │
       ┌───────────────┼────────────────┐
       │               │                │
      NMT             SDO               PDO
       │               │                │
       │          配置/访问对象          │
       │                                │
       │                  ┌─────────────┴────────────┐
       │                  │                          │
       │                TPDO                       RPDO
       │                  │                          │
       │              STM32 → 主站              主站 → STM32
       │                  │                          │
       │              ┌───┴────┐                    │
       │              │        │                    │
       │             DI       AI                   DO
       │              │        │                    │
       │           TPDO1    TPDO2                 RPDO1
       │           0x181    0x281                 0x201
       │            1 byte   4 byte                1 byte
       │
       ├──────── Heartbeat 0x701
       │
       └──────── EMCY 0x081
```

## 

其实就四句话：

**① CAN 怎么连：**

```
500 kbit/s
11-bit Classic CAN
Node-ID = 1
```

**② CAN-ID 怎么分：**

```
0x000 NMT
0x081 EMCY
0x181 TPDO1
0x201 RPDO1
0x281 TPDO2
0x601/581 SDO
0x701 Heartbeat
```

**③ PDO 里面装什么：**

```
TPDO1 → 4 DI
RPDO1 → 4 DO
TPDO2 → 2 AI
```

**④ 什么状态才能用 PDO：**

```
Operational
```

所以，阶段 0 不是在写代码，而是在把“协议合同”定死。

后面真正写 STM32 程序时，就是按照这份合同实现：

```
CAN接收
  ↓
判断 COB-ID
  ↓
NMT / SDO / RPDO1
  ↓
执行对应协议处理

同时

DI变化 ──→ TPDO1
AI已配置定时/已启用变化事件 ──→ TPDO2
节点状态 ─→ Heartbeat
严重故障 ─→ EMCY
```

这样你后面进入阶段 1、阶段 2 写代码时，就不会出现“这个 CAN 帧到底应该干什么”的问题。
