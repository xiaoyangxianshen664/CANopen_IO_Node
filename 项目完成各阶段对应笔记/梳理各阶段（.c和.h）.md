**① 阶段 1：先规定“节点”和“报文”长什么样**

```c
co_types.h		//这个头文件主要定义类型，没有创建一个实际节点。
    │

    │

    │       ├── node_id

```

```c
调用者写：
co_context_t node = {0};
才创建了节点上下文变量。

co_core.c
    │
    ├── co_context_validate()   内部辅助函数
    │       检查上下文指针、发送回调、节点号
    │
    ├── co_init()
    │       检查参数后填写调用者创建的node
    │       保存节点号、初始状态、发送函数和辅助地址
    │
    ├── co_frame_validate()
    │       检查CAN-ID、DLC和帧类型
    │
    ├── co_send()
    │       检查上下文和帧
    │       调用保存的发送回调，返回其状态
    │
    └── co_classify_rx()

```

因此阶段 1 的设计是：

```c
协议核心知道“我要发送这帧”
    ↓
通过函数指针调用外部发送函数
    ↓
具体怎么发送，由外部实现
```

PC 测试和未来 STM32 的区别只在下面这层：

```c
PC测试：
co_send() → fake_tx() → 记录报文和调用次数

未来STM32：
co_send() → 硬件发送回调 → 提交给CAN外设
```

接收方向同样如此：

```c
PC测试：测试代码构造报文 ──┐
                          ├──→ co_classify_rx()
STM32：驱动从CAN取出报文 ──┘
```

`test_co_core.c` 就是通过模拟数据，验证这些检查、保存和分类是否正确。



# 阶段2：

### 阶段 2 的第一层：先定义通用“对象条目”

我们接下来要处理的内容变成了：

> 找到某个对象，读取或修改它的数据。

因此需要另一组类型：

```c
co_od.h
    │
    ├── co_od_type_t
    │       BOOLEAN、UNSIGNED8/16/32、INTEGER16
    │
    ├── co_od_access_t
    │       READ_ONLY、READ_WRITE、CONSTANT
    │
    ├── co_od_read_fn / co_od_write_fn
    │       读写回调必须符合的函数形式
    │
    ├── co_od_entry_t
    │       一个对象条目的描述
    │       ├── Index、Sub-index
    │       ├── 类型、长度、权限、范围
    │       ├── 是否仅预运行可写
    │       ├── read / write：函数地址
    │       └── user：对象数据所在位置
    │
    ├── co_od_table_t
    │       ├── entries：条目数组首地址
    │       └── count：条目数量
    │
    └── 声明 co_od_find/read/write()
```

这里最重要的是：

`co_od_entry_t` 描述怎么访问对象；对象当前值通常放在 `user` 指向的存储里。

`co_od.c` 则实现通用规则：

```c
co_od.c
    │
    ├── co_od_type_length()     内部辅助函数
    │       根据类型确定数据长度
    │
    ├── co_od_decode_le()       内部辅助函数
    │       把小端字节组合成整数
    │
    ├── co_od_find()
    │       根据Index + Sub-index查找
    │       把找到的条目地址交给调用者
    │
    ├── co_od_read()
    │       检查指针、类型、长度、读回调
    │       调用读回调填写输出数组
    │
    └── co_od_write()
            检查指针、类型、长度、权限、状态、写回调
            解释有符号数／布尔值，检查数值范围
            调用写回调更新数据
```

**它不知道“这块板子有几个按键、几个 LED”。** 给它什么表或条目，它就按条目描述执行。

所以 `test_co_od.c` 可以不建立整个设备：

```c
临时测试条目
    ├── 绑定fake_read / fake_write
    └── user指向fake_value_t变量
                    ↓
          测试通用查找、读写和拒绝规则
```





###  阶段 2 的第二层：建立我们这台设备的实际对象表

通用工具有了，还需要准备真正的数据。

```c
co_device_od.h
    │
    ├── CO_DEVICE_OD_COUNT = 36
    │
    ├── co_device_identity_t
    │       厂商编号、产品代码、版本、序列号
    │
    ├── co_device_value_t
    │       ├── value：当前值
    │       └── writes：写回调成功写入次数
    │
    ├── co_device_od_t
    │       ├── fields[36]：数据存储
    │       ├── entries[36]：对象条目
    │       └── table：查找入口
    │
    └── 声明设备对象表的初始化和应用接口
```

调用者创建：

```
co_device_od_t device = {0};
```

就拥有了上述两个数组和一个表结构体，但还需要初始化它们的内容和连接关系。

```c
co_device_od.c
    │
    ├── 槽位常量
    │       标记DI、DO、AI等在数组中的位置
    │
    ├── definition_t + definitions[]
    │       描述36个对象的规则和初值
    │
    ├── read_value()
    │       当前整数 → 小端字节 → 输出数组
    │
    ├── write_value()
    │       输入字节 → 整数 → 对象存储
    │       同时增加writes
    │
    ├── ready()
    │       检查设备指针、表与数组连接、条目数量
    │
    ├── co_device_od_init()
    │       根据模板填写条目、初值、回调和存储地址
    │
    ├── co_device_od_update_inputs()
    │       更新DI和AI，AI原始值乘8后保存
    │
    ├── co_device_od_get_outputs()
    │       取出DO命令，交给应用层
    │
    ├── co_device_od_set_error()
    │       更新错误寄存器
    │
    └── co_device_od_get_heartbeat()
            取出心跳周期和配置写入次数
```

初始化后的实际关系：

```c
definitions[i]：只读规则模板
    │
    │ co_device_od_init()
    ├──→ device.fields[i]
    │       ├── value  = 初始值
    │       └── writes = 0
    │
    └──→ device.entries[i]
            ├── 对象地址、类型、长度、权限、范围
            ├── read  → read_value
            ├── write → write_value，或NULL
            └── user  → device.fields[i]

device.table
    ├── entries → device.entries[0]
    └── count   = 36
```

因此我们现在有了：

```c
co_od.c：怎样查找、检查和访问对象

co_device_od.c：我们这台设备有哪些对象，
                每个对象的数据放在哪里
```



### 把“读取 AI”和“写入 DO”两条实际路径连起来

先看读取 AI1。应用传入 ADC 原始值 `1234`：

```c
应用获得ADC原始值1234
    ↓
co_device_od_update_inputs()
    ↓
device.fields[13].value = 1234 × 8 = 9872
    ↓
co_od_find(&device.table, 0x6401, 1, &entry)
    ↓
找到AI1条目，entry指向它
    ↓
co_od_read(entry, data, 2)
    ↓
entry->read(entry->user, data, 2)
    ↓
read_value()通过user访问fields[13]
    ↓
9872 = 0x2690
    ↓
data[0] = 0x90
data[1] = 0x26
```

到这里，只是把对象值读进数组，没有发送 CAN 报文。	



再看写入 DO 命令 `5`： 

```c
准备输入数组 data[] = {5}
    ↓
co_od_find()找到0x6200:01
    ↓
co_od_write()检查后调用write_value()
    ↓
device.fields[11].value = 5
device.fields[11].writes 加1
    ↓
应用调用co_device_od_get_outputs()
    ↓
调用者的output变量得到5
    ↓
未来GPIO代码根据output控制LED
```

**到写入对象这一步，也只是改了 RAM。** 控制引脚是后续应用和硬件层的工作。

# 阶段3：NMT状态管理和Boot-up

阶段3在阶段1的CAN帧入口之上，真正执行NMT命令、维护节点状态，并完成启动通知。阶段3不负责Heartbeat周期发送、SDO、PDO、GPIO或FreeRTOS。

```text
阶段1：收到CAN帧
    co_classify_rx()
        │
        └── 识别为本节点或广播NMT
                │
                ▼
阶段3：co_nmt_receive()
    ├── 验证NMT上下文
    ├── 复用阶段1分类结果
    ├── 读取frame.data[0]命令
    ├── Start/Stop/Pre-op → change_state()
    └── Reset → 恢复对象范围 → 发送Boot-up
```

### 阶段3的文件关系

```c
`co_nmt.h` 定义：

- `co_nmt_command_t`：Start、Stop、Pre-op、Reset Node、Reset Communication五种命令值；
- `co_nmt_notify_fn`：状态变化通知回调指针函数；
- `co_nmt_t`：连接阶段1节点上下文、阶段2设备对象表、通知回调和用户指针；
- `co_nmt_init()`、`co_nmt_bootup()`、`co_nmt_receive()`接口。
```

```c
`co_nmt.c` 实现：

- `validate()` 检查NMT上下文、发送回调、对象表连接、条目数量、Node-ID和状态值；
- `change_state()` 只在目标状态不同的时候修改 `node->state`，并调用通知回调；
- `co_nmt_init()` 先用临时 `candidate` 验证所有绑定参数，通过后一次性写入NMT上下文，仍保持Initialization；
- `co_nmt_bootup()` 只允许Initialization状态发送一次 `0x700+Node-ID`、DLC=1、数据 `00` 的Boot-up。发送回调返回 `CO_OK` 后才进入Pre-operational；忙或失败时保持Initialization，允许重试；
- `co_nmt_receive()` 调用阶段1的 `co_classify_rx()`，只处理本节点或广播NMT。Initialization阶段忽略命令；其余状态根据命令切换状态，未知命令返回 `CO_IGNORED`。
```



### 两种NMT复位

```c
`Reset Communication`（`0x82`）调用 `co_device_od_reset(device, 1)`，恢复通信区可变参数，例如 `0x1017` 和PDO事件周期，保留应用对象值；

`Reset Node`（`0x81`）调用 `co_device_od_reset(device, 0)`，恢复全部可变对象，包括 `0x6423` 和DO命令。两者都进入Initialization，完成恢复后重新发送Boot-up并进入Pre-operational；都不是MCU硬件复位。

通信复位后保留DO对象值，不代表物理GPIO必须继续输出原状态。状态通知回调应由应用层执行安全输出、清理后续服务计时和队列；真实GPIO安全策略留到硬件集成阶段。
```

# 阶段4：Heartbeat Producer

阶段4把阶段2的心跳周期对象、阶段3的NMT状态和阶段1的发送入口连接起来，形成周期状态上报。

```text
应用层周期调用 co_hb_process(&hb, elapsed_ms)
                    │
                    ▼
         读取 0x1017:00 和写入次数
                    │
                    ▼
              累加 hb->elapsed_ms
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       未到期              已到期
     CO_IGNORED       组装并调用 co_send()
                              │
                              ▼
                0x700 + Node-ID / DLC=1 / node.state
```

- `co_hb.h` 定义 `co_hb_t`：保存节点指针、设备对象表指针、累计毫秒数和已观察的 `0x1017` 写入次数。
- `co_hb.c` 的 `validate()` 检查绑定对象；`co_hb_init()` 完成绑定并记录初始写入次数；`co_hb_process()` 读取周期、处理周期0和Initialization、累计时间、组帧并通过 `co_send()` 发送。
- `test_co_hb.c` 用 `fake_t` 记录发送次数和最后一帧，预设 `CO_OK`、`CO_ERR_TX_BUSY` 等传输结果，验证状态字节、周期重写、关闭和失败重试。

阶段4完成后，阶段1～4的调用关系为：

```text
阶段2：0x1017:00 ──► 阶段4：Heartbeat计时
阶段3：node.state ──► 阶段4：状态字节
阶段1：co_send()  ◄── 阶段4：提交Heartbeat帧
```

阶段4严格构建和13/13 CTest通过，源码与测试学习已完成；尚未接入STM32 HAL/FreeRTOS、真实CAN总线或Heartbeat Consumer。下一入口为阶段5 expedited SDO Server。

# 阶段5：expedited SDO Server

阶段5把阶段1的CAN报文入口、阶段2的对象字典和阶段3的NMT状态连接起来，为主站提供参数读写服务。阶段4的Heartbeat与SDO并列使用同一节点上下文和发送回调，但不改变Heartbeat计时。

```text
主站请求 0x600 + Node-ID
        │
        ▼
阶段1：co_classify_rx() 校验并识别 SDO
        │
        ▼
阶段5：co_sdo_receive()
   ├── 状态门控：Pre-op/Operational 才处理
   ├── Upload：co_od_find() → co_od_read() → 组装 0x580+ID 响应
   └── Download：解析长度 → co_od_find() → co_od_write() → 返回 0x60
        │
        └── 失败：组装 0x80 Abort 和 4 字节小端错误码
```

首版只支持固定8字节 expedited SDO：Upload请求 `0x40`，Download请求 `0x2F/0x2B/0x27/0x23`，Upload成功响应 `0x4F/0x4B/0x47/0x43`，Download成功响应 `0x60`。对象不存在、子索引不存在、只读、长度、值和状态错误分别映射到阶段0规划的Abort码。第一版不实现分段/块传输和SDO客户端。

阶段5严格构建及14/14 CTest通过，源码和测试学习已完成；尚未接入STM32 HAL/FreeRTOS或真实CAN总线。下一阶段为阶段6 PDO和固定映射。

# 阶段6：PDO 和固定映射

阶段6把阶段1的报文分类、阶段2的对象字典和阶段3的 NMT 状态真正连接成实时 I/O 数据通道。

```text
主站 ──RPDO1 0x201──► co_pdo_receive()
                         │
                         └──写入 0x6200:01（DO）

对象字典 0x6000:01（DI）变化
                         │
                         └──co_pdo_process()
                                └──TPDO1 0x181

对象字典 0x6401:01/02（AI）变化或事件周期到期
                         │
                         └──co_pdo_process()
                                └──TPDO2 0x281
```

### 阶段6文件关系

```c
co_pdo.h
    └── co_pdo_t
        ├── node / device：节点和对象字典
        ├── last_di / last_ai1 / last_ai2：上次输入值
        ├── elapsed_tpdo1 / elapsed_tpdo2：两个独立计时器
        ├── pending_tpdo1 / pending_tpdo2：待发送标志
        └── previous_operational：是否已经处理过进入运行状态

co_pdo.c
    ├── validate()：检查 PDO 上下文
    ├── send_tpdo1()：读取 0x6000:01，发送 0x181/DLC=1
    ├── send_tpdo2()：读取 0x6401:01/02，发送 0x281/DLC=4
    ├── co_pdo_init()：绑定节点、对象字典并保存初始输入
    ├── co_pdo_receive()：接收 0x201/DLC=1，检查保留位并写入 DO
    └── co_pdo_process()：状态门控、比较输入、累计周期、发送 TPDO
```

固定映射为：

```text
RPDO1：0x201 → 0x6200:01，1字节
TPDO1：0x181 ← 0x6000:01，1字节
TPDO2：0x281 ← 0x6401:01、0x6401:02，4字节
```

TPDO 只在 Operational 状态处理。刚进入 Operational 时各发送一次；DI 变化触发 TPDO1；`0x6423:00=1` 后 AI 变化触发 TPDO2；`0x1800:05` 和 `0x1801:05` 配置事件周期后，两个 TPDO 还可以独立定时发送。发送忙时保留 pending 标志，后续处理再次尝试。

阶段6的 `co_pdo.h`、`co_pdo.c` 和 `test_co_pdo.c` 已学习完成，15/15 CTest通过；后续阶段7将发送入口从 PC 测试回调替换为 STM32 bxCAN。

# 阶段7：STM32 bxCAN 传输层

阶段7把纯 C 协议栈的 `co_send()` 接到 STM32F429 的 CAN1，并把硬件接收中断转换为协议层使用的 `can_frame_t`。

```text
CAN1 FIFO0 接收中断
    ↓
HAL_CAN_RxFifo0MsgPendingCallback()
    ↓
读取 HAL_CAN_RxHeaderTypeDef 和数据
    ↓
写入 BSP 软件环形队列
    ↓
CanopenTask 调用 CAN_ReceiveFrame()
    ↓
dispatch_frame() 分发 NMT / SDO / PDO
```

```c
bsp_can.h
    ├── CAN_Init() / CAN_Start()
    ├── CAN_SendFrame()
    ├── CAN_ReceiveFrame()
    └── can_rx_overflow_count、can_tx_busy_count、can_error_count、can_bus_off_count

bsp_can.c
    ├── 配置 CAN1、PB8/PB9、AF9、500 kbit/s
    ├── 配置过滤器和 FIFO0 通知
    ├── CAN_SendFrame()：检查 DLC、邮箱并转换 HAL 帧
    ├── HAL_CAN_RxFifo0MsgPendingCallback()：只取帧并入队
    ├── HAL_CAN_ErrorCallback()：统计 CAN 错误和 Bus-off
    └── CAN_ReceiveFrame()：从 head/tail 环形队列取帧
```

`canopen_app.h/.c` 是应用层包装，不重新实现协议。它保存节点、对象字典、NMT、Heartbeat、SDO、PDO 上下文，并向任务层提供：

```c
Canopen_App_Init()
Canopen_App_NmtReceive()
Canopen_App_SdoReceive()
Canopen_App_PdoReceive()
Canopen_App_ProcessHeartbeat()
Canopen_App_ProcessPdo()
Canopen_App_UpdateInputs()
Canopen_App_GetOutputs()
```

阶段7定位并修复了系统时钟初始化问题，正式工程按 180 MHz 系统时钟、APB1=45 MHz 运行，USB-CAN 实机完成 Boot-up、NMT、Heartbeat、SDO、RPDO、TPDO 验证。当前开发板实际资源为 PA0/PC13 两路 DI、PC3/PA4 两路 AI、PH10/PH11/PH12 RGB DO；四路 DI/DO 留给后续专用 PCB。

# 阶段8：FreeRTOS 与真实 I/O

阶段8在阶段7 CAN 传输层上接入任务系统和真实硬件。核心文件关系如下：

```c
ADC_Multi.h
    ├── ADC1 双通道定义：PC3 电位器、PA4 温度传感器
    ├── TIM3 触发参数和 DMA2 Stream0 参数
    ├── ADC_READY_FIRST_HALF / ADC_READY_SECOND_HALF
    └── ADC_Multi_Init() / ADC_Multi_ReadAverage()

ADC_Multi.c
    ├── 配置 GPIO、ADC 扫描序列和 DMA 循环缓冲
    ├── TIM3 TRGO 每 1 ms 触发一轮 AI1/AI2 转换
    ├── DMA 半传输/全传输中断回调
    └── adc_dma_notify_from_isr(area_flag) 通知 IOTask

freertos_demo.h
    ├── freertos_demo()
    └── 暴露采样、监视和 CAN 诊断快照

freertos_demo.c
    ├── read_board_di()：读取 KEY1/KEY2 并打包 DI
    ├── apply_board_do()：根据 DO 位控制 RGB GPIO
    ├── IO_Task()：处理 ADC 通知、DI/AI 采样和 DO 队列
    ├── Canopen_Task()：处理 CAN、协议定时器、对象字典和队列
    ├── Monitor_Task()：检查采样计数是否增长
    ├── Diagnostics_Task()：复制 CAN 错误诊断快照
    └── freertos_demo()：初始化应用、创建队列/任务并启动调度器
```

ADC 缓冲区采用交替布局：

```text
[AI1_0][AI2_0]...[AI1_31][AI2_31] | [AI1_32][AI2_32]...
<----------- 前半区 ----------->   <--------- 后半区 --------->
```

DMA 半区完成后只通过任务通知传递位图；`IOTask` 选择已完成的半区，计算 32 组 AI1/AI2 平均值，再读取当前 DI，使用 `xQueueOverwrite()` 把最新 `io_sample_t` 交给 `CanopenTask`。DO 队列则只保存一个最新的 `uint8_t` 输出值。

任务运行关系：

```text
CanopenTask（优先级3）
    约每 1 ms 执行一轮，末尾用 vTaskDelayUntil() 等待下一周期

IOTask（优先级2）
    由 ADC DMA 通知提前唤醒，或在 xTaskNotifyWait() 最多阻塞 10 ms

MonitorTask / DiagnosticsTask（优先级1）
    每约 1 s 运行一轮，执行健康检查和诊断快照
```

应用层真实链路为：

```text
按键、ADC
    ↓
IOTask
    ↓
io_sample_queue
    ↓
CanopenTask
    ↓
Canopen_App_UpdateInputs()
    ↓
对象字典 0x6000 / 0x6401
    ↓
Canopen_App_ProcessPdo()
    ↓
TPDO1 / TPDO2
```

```text
RPDO1 0x201
    ↓
CanopenTask → 0x6200:01
    ↓
io_output_queue
    ↓
IOTask → apply_board_do()
    ↓
RGB 灯 GPIO
```

阶段8重新烧录后的 USB-CAN 回归测试全部通过：NMT/Heartbeat、SDO 读取 DI/AI/DO、RPDO 控制 RGB 灯、TPDO1/TPDO2 500 ms 自动上报，以及 KEY1、KEY2、电位器和温度传感器变化均正常。阶段8代码学习和真实 I/O 验证完成，下一阶段为 EMCY、错误寄存器、Bus-off/FIFO 溢出、通信超时、安全输出和恢复策略。
