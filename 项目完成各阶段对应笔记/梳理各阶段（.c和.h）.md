# 阶段1：

**① 阶段 1：先规定“节点”和“报文”长什么样**

```c
co_types.h		//这个头文件主要定义类型，没有创建一个实际节点。
    │
    ├── co_status_t
    │       函数执行结果：成功、参数错误、长度错误……
    │
    ├── co_nmt_state_t
    │       节点状态：初始化、预运行、运行、停止
    │
    ├── can_frame_t
    │       一帧CAN报文：ID、长度、数据、帧类型
    │
    ├── co_tx_fn
    │       发送回调的函数指针类型
    │
    ├── co_context_t
    │       节点上下文
    │       ├── node_id
    │       ├── state
    │       ├── tx：发送函数地址
    │       └── tx_user：发送函数需要的辅助数据地址
    │
    └── co_rx_kind_t
            接收分类结果：NMT、SDO、RPDO1、无关帧
```

```c
调用者写：
co_context_t node = {0};
才创建了节点上下文变量。

co_core.c
    │
    ├── co_context_validate()   内部辅助函数
    │       检查上下文指针、发送回调、节点号
    │
    ├── co_init()
    │       检查参数后填写调用者创建的node
    │       保存节点号、初始状态、发送函数和辅助地址
    │
    ├── co_frame_validate()
    │       检查CAN-ID、DLC和帧类型
    │
    ├── co_send()
    │       检查上下文和帧
    │       调用保存的发送回调，返回其状态
    │
    └── co_classify_rx()
            对已经放入can_frame_t的报文进行检查和分类
            判断是否属于本节点的NMT、SDO或RPDO1
```

因此阶段 1 的设计是：

```c
协议核心知道“我要发送这帧”
    ↓
通过函数指针调用外部发送函数
    ↓
具体怎么发送，由外部实现
```

PC 测试和未来 STM32 的区别只在下面这层：

```c
PC测试：
co_send() → fake_tx() → 记录报文和调用次数

未来STM32：
co_send() → 硬件发送回调 → 提交给CAN外设
```

接收方向同样如此：

```c
PC测试：测试代码构造报文 ──┐
                          ├──→ co_classify_rx()
STM32：驱动从CAN取出报文 ──┘
```

`test_co_core.c` 就是通过模拟数据，验证这些检查、保存和分类是否正确。



# 阶段2：

### 阶段 2 的第一层：先定义通用“对象条目”

我们接下来要处理的内容变成了：

> 找到某个对象，读取或修改它的数据。

因此需要另一组类型：

```c
co_od.h
    │
    ├── co_od_type_t
    │       BOOLEAN、UNSIGNED8/16/32、INTEGER16
    │
    ├── co_od_access_t
    │       READ_ONLY、READ_WRITE、CONSTANT
    │
    ├── co_od_read_fn / co_od_write_fn
    │       读写回调必须符合的函数形式
    │
    ├── co_od_entry_t
    │       一个对象条目的描述
    │       ├── Index、Sub-index
    │       ├── 类型、长度、权限、范围
    │       ├── 是否仅预运行可写
    │       ├── read / write：函数地址
    │       └── user：对象数据所在位置
    │
    ├── co_od_table_t
    │       ├── entries：条目数组首地址
    │       └── count：条目数量
    │
    └── 声明 co_od_find/read/write()
```

这里最重要的是：

`co_od_entry_t` 描述怎么访问对象；对象当前值通常放在 `user` 指向的存储里。

`co_od.c` 则实现通用规则：

```c
co_od.c
    │
    ├── co_od_type_length()     内部辅助函数
    │       根据类型确定数据长度
    │
    ├── co_od_decode_le()       内部辅助函数
    │       把小端字节组合成整数
    │
    ├── co_od_find()
    │       根据Index + Sub-index查找
    │       把找到的条目地址交给调用者
    │
    ├── co_od_read()
    │       检查指针、类型、长度、读回调
    │       调用读回调填写输出数组
    │
    └── co_od_write()
            检查指针、类型、长度、权限、状态、写回调
            解释有符号数／布尔值，检查数值范围
            调用写回调更新数据
```

**它不知道“这块板子有几个按键、几个 LED”。** 给它什么表或条目，它就按条目描述执行。

所以 `test_co_od.c` 可以不建立整个设备：

```c
临时测试条目
    ├── 绑定fake_read / fake_write
    └── user指向fake_value_t变量
                    ↓
          测试通用查找、读写和拒绝规则
```





###  阶段 2 的第二层：建立我们这台设备的实际对象表

通用工具有了，还需要准备真正的数据。

```c
co_device_od.h
    │
    ├── CO_DEVICE_OD_COUNT = 36
    │
    ├── co_device_identity_t
    │       厂商编号、产品代码、版本、序列号
    │
    ├── co_device_value_t
    │       ├── value：当前值
    │       └── writes：写回调成功写入次数
    │
    ├── co_device_od_t
    │       ├── fields[36]：数据存储
    │       ├── entries[36]：对象条目
    │       └── table：查找入口
    │
    └── 声明设备对象表的初始化和应用接口
```

调用者创建：

```
co_device_od_t device = {0};
```

就拥有了上述两个数组和一个表结构体，但还需要初始化它们的内容和连接关系。

```c
co_device_od.c
    │
    ├── 槽位常量
    │       标记DI、DO、AI等在数组中的位置
    │
    ├── definition_t + definitions[]
    │       描述36个对象的规则和初值
    │
    ├── read_value()
    │       当前整数 → 小端字节 → 输出数组
    │
    ├── write_value()
    │       输入字节 → 整数 → 对象存储
    │       同时增加writes
    │
    ├── ready()
    │       检查设备指针、表与数组连接、条目数量
    │
    ├── co_device_od_init()
    │       根据模板填写条目、初值、回调和存储地址
    │
    ├── co_device_od_update_inputs()
    │       更新DI和AI，AI原始值乘8后保存
    │
    ├── co_device_od_get_outputs()
    │       取出DO命令，交给应用层
    │
    ├── co_device_od_set_error()
    │       更新错误寄存器
    │
    └── co_device_od_get_heartbeat()
            取出心跳周期和配置写入次数
```

初始化后的实际关系：

```c
definitions[i]：只读规则模板
    │
    │ co_device_od_init()
    ├──→ device.fields[i]
    │       ├── value  = 初始值
    │       └── writes = 0
    │
    └──→ device.entries[i]
            ├── 对象地址、类型、长度、权限、范围
            ├── read  → read_value
            ├── write → write_value，或NULL
            └── user  → device.fields[i]

device.table
    ├── entries → device.entries[0]
    └── count   = 36
```

因此我们现在有了：

```c
co_od.c：怎样查找、检查和访问对象

co_device_od.c：我们这台设备有哪些对象，
                每个对象的数据放在哪里
```



### 把“读取 AI”和“写入 DO”两条实际路径连起来

先看读取 AI1。应用传入 ADC 原始值 `1234`：

```c
应用获得ADC原始值1234
    ↓
co_device_od_update_inputs()
    ↓
device.fields[13].value = 1234 × 8 = 9872
    ↓
co_od_find(&device.table, 0x6401, 1, &entry)
    ↓
找到AI1条目，entry指向它
    ↓
co_od_read(entry, data, 2)
    ↓
entry->read(entry->user, data, 2)
    ↓
read_value()通过user访问fields[13]
    ↓
9872 = 0x2690
    ↓
data[0] = 0x90
data[1] = 0x26
```

到这里，只是把对象值读进数组，没有发送 CAN 报文。	



再看写入 DO 命令 `5`： 

```c
准备输入数组 data[] = {5}
    ↓
co_od_find()找到0x6200:01
    ↓
co_od_write()检查后调用write_value()
    ↓
device.fields[11].value = 5
device.fields[11].writes 加1
    ↓
应用调用co_device_od_get_outputs()
    ↓
调用者的output变量得到5
    ↓
未来GPIO代码根据output控制LED
```

**到写入对象这一步，也只是改了 RAM。** 控制引脚是后续应用和硬件层的工作。

# 阶段3：NMT状态管理和Boot-up

阶段3在阶段1的CAN帧入口之上，真正执行NMT命令、维护节点状态，并完成启动通知。阶段3不负责Heartbeat周期发送、SDO、PDO、GPIO或FreeRTOS。

```text
阶段1：收到CAN帧
    co_classify_rx()
        │
        └── 识别为本节点或广播NMT
                │
                ▼
阶段3：co_nmt_receive()
    ├── 验证NMT上下文
    ├── 复用阶段1分类结果
    ├── 读取frame.data[0]命令
    ├── Start/Stop/Pre-op → change_state()
    └── Reset → 恢复对象范围 → 发送Boot-up
```

### 阶段3的文件关系

```c
`co_nmt.h` 定义：

- `co_nmt_command_t`：Start、Stop、Pre-op、Reset Node、Reset Communication五种命令值；
- `co_nmt_notify_fn`：状态变化通知回调指针函数；
- `co_nmt_t`：连接阶段1节点上下文、阶段2设备对象表、通知回调和用户指针；
- `co_nmt_init()`、`co_nmt_bootup()`、`co_nmt_receive()`接口。
```

```c
`co_nmt.c` 实现：

- `validate()` 检查NMT上下文、发送回调、对象表连接、条目数量、Node-ID和状态值；
- `change_state()` 只在目标状态不同的时候修改 `node->state`，并调用通知回调；
- `co_nmt_init()` 先用临时 `candidate` 验证所有绑定参数，通过后一次性写入NMT上下文，仍保持Initialization；
- `co_nmt_bootup()` 只允许Initialization状态发送一次 `0x700+Node-ID`、DLC=1、数据 `00` 的Boot-up。发送回调返回 `CO_OK` 后才进入Pre-operational；忙或失败时保持Initialization，允许重试；
- `co_nmt_receive()` 调用阶段1的 `co_classify_rx()`，只处理本节点或广播NMT。Initialization阶段忽略命令；其余状态根据命令切换状态，未知命令返回 `CO_IGNORED`。
```



### 两种NMT复位

```c
`Reset Communication`（`0x82`）调用 `co_device_od_reset(device, 1)`，恢复通信区可变参数，例如 `0x1017` 和PDO事件周期，保留应用对象值；

`Reset Node`（`0x81`）调用 `co_device_od_reset(device, 0)`，恢复全部可变对象，包括 `0x6423` 和DO命令。两者都进入Initialization，完成恢复后重新发送Boot-up并进入Pre-operational；都不是MCU硬件复位。

通信复位后保留DO对象值，不代表物理GPIO必须继续输出原状态。状态通知回调应由应用层执行安全输出、清理后续服务计时和队列；真实GPIO安全策略留到硬件集成阶段。
```

# 阶段4：Heartbeat Producer

阶段4把阶段2的心跳周期对象、阶段3的NMT状态和阶段1的发送入口连接起来，形成周期状态上报。

```text
应用层周期调用 co_hb_process(&hb, elapsed_ms)
                    │
                    ▼
         读取 0x1017:00 和写入次数
                    │
                    ▼
              累加 hb->elapsed_ms
                    │
          ┌─────────┴─────────┐
          ▼                   ▼
       未到期              已到期
     CO_IGNORED       组装并调用 co_send()
                              │
                              ▼
                0x700 + Node-ID / DLC=1 / node.state
```

- `co_hb.h` 定义 `co_hb_t`：保存节点指针、设备对象表指针、累计毫秒数和已观察的 `0x1017` 写入次数。
- `co_hb.c` 的 `validate()` 检查绑定对象；`co_hb_init()` 完成绑定并记录初始写入次数；`co_hb_process()` 读取周期、处理周期0和Initialization、累计时间、组帧并通过 `co_send()` 发送。
- `test_co_hb.c` 用 `fake_t` 记录发送次数和最后一帧，预设 `CO_OK`、`CO_ERR_TX_BUSY` 等传输结果，验证状态字节、周期重写、关闭和失败重试。

阶段4完成后，阶段1～4的调用关系为：

```text
阶段2：0x1017:00 ──► 阶段4：Heartbeat计时
阶段3：node.state ──► 阶段4：状态字节
阶段1：co_send()  ◄── 阶段4：提交Heartbeat帧
```

阶段4严格构建和13/13 CTest通过，源码与测试学习已完成；尚未接入STM32 HAL/FreeRTOS、真实CAN总线或Heartbeat Consumer。下一入口为阶段5 expedited SDO Server。
