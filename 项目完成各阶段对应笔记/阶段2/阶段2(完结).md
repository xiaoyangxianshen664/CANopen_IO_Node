最开始，我们先按你的硬件和功能需求搭出一套能运行、能测试的对象字典；拿到规范正文后，再检查每个对象的具体定义，把“项目自己约定的写法”修正为有明确规范依据的写法。

整体架构没有变化，变化主要集中在数据表示、配置默认值、访问权限和缺少的配置对象。笔记虽然拆成十几个点，背后其实只有几类原因。



## 1：最初规划：先让你的硬件在对象字典里有对应的位置

你的硬件需求是：

```c
STM32F429
    ├── 4路按键输入 DI
    ├── 4路LED输出 DO
    ├── 2路ADC输入 AI
    └── CAN通信
```

所以我们先规划：

```c
硬件／配置                  对象字典
4路DI状态          →       0x6000:01
4路DO命令          →       0x6200:01
AI1采样值          →       0x6401:01
AI2采样值          →       0x6401:02
心跳周期           →       0x1017:00
PDO通信和映射参数  →       0x1400、0x1800等
```

同时把代码分成两层：

```c
co_od.c
    └── 通用规则：查找、读、写、权限、长度、范围检查

co_device_od.c
    └── 本设备具体对象：有哪些对象、初始值是什么、数据存在哪里
```

这套分层和 `definitions → entries / fields → table` 的关系，规范核验后仍然保留。 你前面花时间弄懂的主线没有白学。

但初版中有些细节按工程直觉先做了，例如：

- ADC 是 `0～4095`，那就直接把这个值存进 AI 对象。
- 希望上位机每 `100 ms` 看到模拟量，那就把 TPDO2 默认周期设成 `100 ms`。
- PDO 参数在预运行时修改比较合适，那就统一限制为 Pre-operational。
- 主站不能写的对象，统一标成只读。

这些写法能构成自洽的程序，**但“程序自洽”还不足以证明“对象定义符合规范”。** 所以前面保留了开发版状态。







## 2：三份 PDF 分别补上了什么依据

| 规范          | 主要帮助我们核对什么                                    |
| ------------- | ------------------------------------------------------- |
| **CiA 301**   | CANopen 通用通信规则、数据类型、PDO 参数、错误寄存器    |
| **CiA 401-1** | DI、DO、AI 设备应该提供哪些对象，以及这些对象的默认行为 |
| **CiA 306**   | EDS 这份“设备说明书”应该如何描述对象和设备能力          |

```c
401：I/O设备在这些规则之上的具体约定

```





## 3：AI 为什么从直接保存原始值，改成乘 8？

最初为了直观，我们采用：

```c
ADC读到1234
    ↓
AI对象保存1234
    ↓
上位机读到1234
```

但 CiA 401-1 的 `0x6401` 定义不仅要求使用 `INTEGER16`，还要求不足 16 位的数据左对齐。

我们一开始就用两个字节保存 AI 值了。这次没有把两个字节改成更多字节。

这里容易混淆的是三个概念：

| 概念                       | 回答的问题                           |
| -------------------------- | ------------------------------------ |
| 长度为 2 字节              | 用多少空间表示这个对象？             |
| `UNSIGNED16` / `INTEGER16` | 这 16 位按无符号数还是有符号数解释？ |
| 左对齐                     | 有效数据放在这 16 位中的哪个位置？   |



我们选用的标准对象 `0x6401`，在 CiA 401-1 中规定的数据类型就是 `INTEGER16`（有符号 16 位整数）。

既然用这个标准对象表示模拟量，就应该按它规定的类型实现。最初草案写成 `UNSIGNED16`，是我们早期定义不准确，后来进行了修正。

为什么标准对象会使用有符号类型？因为模拟量设备不只有我们这种 **0～3.3 V** 输入，还可能采集正负信号，例如：

```c
我们的输入：       0～3.3 V → 只有非负值

其他模拟量设备：  -10～+10 V → 需要表示负值和正值
```

使用 `INTEGER16`，同一个标准对象就能表示正数和负数。

**但有符号类型并不要求你必须使用负数。**

```
int16_t value = 1234;
```

完全合法。它能表示 `-32768～32767`，我们的非负数也在其中。

对我们项目而言：

```c
选择标准AI对象 0x6401
    ↓
按规范使用 INTEGER16
    ↓
我们的硬件只有非负输入
    ↓
采用正值范围，符号位保持0
```

所以，**改成有符号不是因为 STM32 的 ADC 突然会采出负数，而是为了符合 `0x6401` 的标准类型定义。**





本次改动最主要是：改变“有效数据的位置”。

例如 ADC 原始值为 `1234`，十六进制是 `0x04D2`。

原来的表示：

```c
两个字节，共16位：

0000 0100 1101 0010
└──┘ └───────────┘
高位补0   12位ADC数据
```

现在采用的项目表示：

```c
0 | 0100 1101 0010 | 000
↑   ↑                ↑
正号 12位ADC数据       低3位补0
```

对应运算：

```
1234 << 3
```

结果为：

```
9872，也就是0x2690
```

所以两版的区别是：

```c
以前：两个字节里保存 0x04D2，读到1234
现在：两个字节里保存 0x2690，读到9872
```

上位机按我们约定除以 `8`，就能恢复原始 ADC 值 `1234`。

**因此，“已经用两个字节”只能说明空间足够，并不能说明有效数据已经按要求对齐。** 另外，这里说的两个字节是对象读写、传输的长度；你学过的 `fields[i].value` 定义的仍是 `uint32_t`，RAM 中占四个字节。



## 4：为什么新增 `0x6423`，对象数量从 35 变成 36？

初版只考虑：

> 模拟量值放在哪里，以及多久发送一次。

正文进一步规定，有模拟量输入的设备还要提供**模拟量变化触发总开关**：

```
0x6423:00
    ├── 0：关闭模拟量变化触发
    └── 1：开启模拟量变化触发
```

所以补上了这个对象，并增加 `BOOLEAN` 类型支持。

这里有两个不同的发送原因：

```
模拟量发生变化 → 由0x6423控制变化触发

事件周期到期   → 由TPDO事件周期配置控制
```

**`0x6423` 不负责开关 ADC，也不是开关 STM32 的硬件中断。** 当前阶段只保存这个配置，阶段 6 才实现如何根据它发送 PDO。



## 5：为什么 TPDO2 默认周期从 100 ms 改成 0？

初始想法是“我们需要每 100 ms 上传一次”，于是直接写进默认值。

正文里的默认事件周期是 `0`，因此现在把**设备出厂／复位默认值**和**实际使用时的配置**分开：

```c
初始化默认：事件周期 = 0
    ↓
应用或主站需要100ms周期
    ↓
在预运行状态配置为100
    ↓
后续PDO服务按100ms工作
```

所以，**每 100 ms 上传模拟量这个需求仍然可以实现，只是不再把 100 ms 当作规范默认值。**







## 6：为什么抑制时间反而改成不允许写了？

这是初版判断不够完整的一处。

最初：

```c
处于Pre-operational
    ↓
允许修改抑制时间
```

但 CiA 301 还有一个具体条件：

> 修改抑制时间前，PDO 必须处于禁用状态。

**“节点处于预运行”与“PDO 的禁用标志已设置”不是同一件事。**

而我们项目原本就选择了固定 COB-ID，没有设计可写的 PDO 禁用／重新启用流程。



因此有两种做法：

| 方案                  | 需要做什么                        |
| --------------------- | --------------------------------- |
| 支持可配置抑制时间    | 增加 PDO 禁用、配置、重新启用流程 |
| 保持当前固定 PDO 方案 | 抑制时间固定为 0，不提供写入口    |

这次选择第二种，保持第一版范围清晰。**固定为 0 是我们的实现取舍，不是规范要求所有设备都只能用 0。**

事件周期和抑制时间的规则不同，所以事件周期仍保留配置能力。



**PDO 的抑制时间，就是限制同一个 TPDO 不要发送得太频繁：两次发送之间，至少隔这么长时间。**

拿我们的 **DI 按键变化 → TPDO1 上报** 举例。假设抑制时间配置为 **10 ms**：

```
时间        输入变化                  TPDO1行为

0 ms        按键状态变化              发送一次
2 ms        又发生变化                暂不发送，记录最新状态
5 ms        再发生变化                暂不发送，更新最新状态
10 ms       抑制间隔结束              若有待发变化，发送最新状态
```

这样就不会在 `0、2、5 ms` 连续发三帧，而是限制发送频率。**在我们的后续实现中，等待期间应保留最新值，避免最后一次变化丢失。**

它和你刚看过的“事件周期”用途不同：

| 参数         | 作用                                 |
| ------------ | ------------------------------------ |
| **抑制时间** | 限制发送频率：不能发得太密           |
| **事件周期** | 定时触发发送：周期到了就产生发送请求 |

**抑制时间结束，本身不代表一定要发送。** 如果没有待发送的数据或其他触发，就不用发。

在对象字典中：

```
0x1800:03 → TPDO1 抑制时间
0x1801:03 → TPDO2 抑制时间
```

单位是 **100 μs**，因此：

```
填写100 → 100 × 100 μs = 10 ms
填写0   → 不使用抑制时间限制
```

我们现在的固定 PDO 版本把这两个值固定为 **0**。上面的 `10 ms` 只是帮助理解作用的例子，当前版本不能通过对象写接口把它改成 `100`。





总览：如果要保留可以在预操作的时候修改抑制时间，需要写一个PDO使用和关闭的开关函数，为了不增加（增加 PDO 禁用、配置、重新启用流程  ），直接把抑制时间可修改功能删掉了，默认值写为0

当前做法就是：为保持固定 PDO 配置，把“修改抑制时间”的入口去掉，抑制时间固定为 `0`。

稍微 纠正一点：如果以后恢复这个功能，核心是支持修改 **PDO 的 COB-ID 配置中的 bit31（有效／禁用标志）**，不一定必须写成一个单独的“开关函数”。

完整配置过程可以是：

```c
节点进入 Pre-operational
    ↓
把对应 PDO 的 COB-ID bit31 设为1
禁用这个 PDO
    ↓
修改抑制时间
    ↓
把 bit31 清为0
重新启用这个 PDO
    ↓
节点进入 Operational，按配置工作
```

**进入预运行状态，并不自动把 bit31 设为 1**，所以原来“只检查 Pre-operational 就允许修改”的实现不够完整。

当前版本则是：

```c
COB-ID 固定，不提供上述禁用／启用配置流程
    ↓
抑制时间固定为0，拒绝写入
    ↓
不通过抑制时间限制发送间隔
```

不是删除了这个对象：**`0x1800:03`、`0x1801:03` 仍然存在、仍能读取，只是不能修改，读到的值都是 `0`。**

后续需要控制 PDO 的发送频率时，再补上**禁用 → 修改抑制时间 → 重新启用**的配置流程。

当前先保留抑制时间固定为 `0`，按计划继续阶段 3。到阶段 6 实现 PDO 时，再结合实际发送需求评估是否完善，不影响现在往下学习。





## 7：为什么要区分 `READ_ONLY` 和 `CONSTANT`？

初版关注的是：

> 主站能不能写？

因此所有不能写的东西都标成只读。

核对规范和 EDS 后，需要进一步说明：

```
READ_ONLY：
    主站不能写，但值会变
    例如DI、AI、错误寄存器

CONSTANT：
    当前设备配置中的固定值
    例如固定映射、固定传输类型
```

所以增加 `CO_OD_CONSTANT`，让 C 对象表和 EDS 都能表达这个区别。

**它们通过主站写接口时都被拒绝。** 原来的通用读写流程基本不用重写，只是描述更准确了。

EDS 的 `Granularity` 也类似：初版把它理解得过于接近“按字节映射”，写成了 `8`；正文明确说不可修改映射应填 `0`，因此修正为 `0`。

我们先按“主站能不能通过 SDO 写入”来区分：

```c
CO_OD_READ_WRITE
    └── 主站可以读，也可以写

CO_OD_READ_ONLY
    └── 主站可以读，但不能写
        设备运行过程中，值可能变化

CO_OD_CONSTANT
    └── 主站可以读，但不能写
        当前设备配置中，这个值固定不变
```

举几个项目中的例子：

```c
0x6000:01  DI
    └── 主站不能写，但按键状态会变化
        → CO_OD_READ_ONLY

0x6401:01  AI1
    └── 主站不能写，但 ADC 采样值会变化
        → CO_OD_READ_ONLY

0x1001:00  错误寄存器
    └── 主站不能写，应用可能更新错误状态
        → CO_OD_READ_ONLY

0x1800:01  TPDO1 COB-ID
    └── 当前项目固定配置，不会动态改变
        → CO_OD_CONSTANT

0x1800:02  TPDO1 传输类型
    └── 当前项目固定为255
        → CO_OD_CONSTANT

0x1A01:01  TPDO 映射值
    └── 当前项目固定映射
        → CO_OD_CONSTANT
```

所以：

```
READ_ONLY 和 CONSTANT 对主站的写入结果相同：
都拒绝写入。
```

但它们表达的**设计含义不同**：

```
READ_ONLY：
    “这个值不能由主站写，但设备运行时可能变。”

CONSTANT：
    “这个值在当前设备配置中就是固定的。”
```

代码中新增：

```
CO_OD_CONSTANT = 2
```

主要是为了让对象表和 EDS 描述得更准确，而不是为了增加一种新的写入流程。因为 `co_od_write()` 现在的判断是：

```
if (entry->access != CO_OD_READ_WRITE)
    return CO_ERR_OD_READ_ONLY;
```

因此 `CO_OD_READ_ONLY` 和 `CO_OD_CONSTANT` 都会被拒绝写入。

还要注意一点：

> `CO_OD_READ_ONLY` 是针对主站对象字典写入接口的限制，不代表应用程序不能更新它。

例如：

```
co_device_od_update_inputs(&device, di, ai1, ai2);
```

应用仍然可以更新 DI、AI；错误处理代码也可以更新错误寄存器。只是主站不能通过普通对象写入接口修改它们。

而 `CO_OD_CONSTANT` 只是表示当前配置固定。以后如果我们实现了动态 PDO 配置，某些对象可能从 `CONSTANT` 变成可配置的 `READ_WRITE`，但这需要同步修改代码、EDS、测试和配置流程。





## 8：错误寄存器为什么增加了检查？

初版只检查 CiA 301 中的保留位 bit6，然后原样保存错误值。

结合两份正文后，规则更完整：

- CiA 301：bit6 保留，不能置 1。
- CiA 401：本设备规范中的 bit5 也保留。
- 出现具体错误时，需要同时表示“存在通用错误”，即置 bit0。

所以现在：

```c
传入通信错误0x10 → 保存0x11
传入0x20或0x40  → 拒绝
传入0           → 清除错误
```

这些修改保证错误寄存器表达符合规则；发送 EMCY 仍是后面的工作。

| 条目        | 含义                       | 类型／权限                    |
| ----------- | -------------------------- | ----------------------------- |
| `0x1000:00` | Device Type，设备类型      | `UNSIGNED32`，固定            |
| `0x1001:00` | Error Register，错误寄存器 | `UNSIGNED8`，只读，应用可更新 |

`0x1000:00` 当前值：

```
0x00070191
```

其中包含：

```c
401       → 通用 I/O 设备类型
DI        → 支持数字输入
DO        → 支持数字输出
AI        → 支持模拟输入
```

错误寄存器虽然对主站只读，但 STM32 应用发生错误时可以更新它。

### 2. 心跳和身份对象

### 3. DI 数字输入对象

| 条目        | 含义                    | 类型／权限                   |
| ----------- | ----------------------- | ---------------------------- |
| `0x6000:00` | DI 子项数量／最高子索引 | `UNSIGNED8`，固定，值为1     |
| `0x6000:01` | 四路 DI 的逻辑状态      | `UNSIGNED8`，只读，范围0～15 |

真正的 DI 数据是：

```
0x6000:01
```

```
bit0 → DI1
bit1 → DI2
bit2 → DI3
bit3 → DI4
```

`0x6000:00` 不是按键状态，而是说明这个对象有一个实际数据子项。

| 条目        | 含义                    | 类型／权限                     |
| ----------- | ----------------------- | ------------------------------ |
| `0x6200:00` | DO 子项数量／最高子索引 | `UNSIGNED8`，固定，值为1       |
| `0x6200:01` | 四路 DO 输出命令        | `UNSIGNED8`，可读写，范围0～15 |

真正的 DO 命令是：

```
0x6200:01
```

低四位对应四个输出：

```
bit0 → DO1
bit1 → DO2
bit2 → DO3
bit3 → DO4
```

主站通过 SDO 或 RPDO 写入这个对象，后续应用层再根据它控制 LED。

------



### 5. AI 模拟量输入对象

| 条目        | 含义                    | 类型／权限                      |
| ----------- | ----------------------- | ------------------------------- |
| `0x6401:00` | AI 子项数量／最高子索引 | `UNSIGNED8`，固定，值为2        |
| `0x6401:01` | AI1                     | `INTEGER16`，只读，范围0～32760 |
| `0x6401:02` | AI2                     | `INTEGER16`，只读，范围0～32760 |

对应实际硬件：

```
0x6401:01 → PC0 → ADC1
0x6401:02 → PC1 → ADC2
```

应用接口接收的 ADC 原始值仍然是：

```
0～4095
```

写入对象前转换为：

```
object_value = adc_value << 3;
```

因此：

```
ADC原始值 0    → 对象值 0
ADC原始值 2048  → 对象值 0x4000
ADC原始值 4095  → 对象值 0x7FF8
```

------



### 6. RPDO1 通信参数

| 条目        | 含义                           | 类型／权限                 |
| ----------- | ------------------------------ | -------------------------- |
| `0x1400:00` | RPDO1 参数子项数量／最高子索引 | `UNSIGNED8`，固定，值为2   |
| `0x1400:01` | RPDO1 COB-ID                   | `UNSIGNED32`，固定         |
| `0x1400:02` | RPDO1 Transmission Type        | `UNSIGNED8`，固定，值为255 |

RPDO1 是：

```
主站 → 从站
```

当前 Node-ID 为1时：

```
RPDO1 CAN-ID = 0x200 + 1 = 0x201
```

它的映射对象在 `0x1600` 中描述。

------



### 7. RPDO1 映射参数

| 条目        | 含义           | 类型／权限                            |
| ----------- | -------------- | ------------------------------------- |
| `0x1600:00` | RPDO1 映射数量 | `UNSIGNED8`，固定，值为1              |
| `0x1600:01` | 第一个映射对象 | `UNSIGNED32`，固定，值为 `0x62000108` |

把：

```
0x62000108
```

拆开：

```
0x6200 → Index
0x01   → Sub-index
0x08   → 映射长度8 bit，也就是1字节
```

所以：

```
RPDO1 的数据 → 写入 0x6200:01，也就是四路 DO 命令
```

------



### 8. TPDO1 通信参数

| 条目        | 含义                           | 类型／权限                         |
| ----------- | ------------------------------ | ---------------------------------- |
| `0x1800:00` | TPDO1 参数子项数量／最高子索引 | `UNSIGNED8`，固定，值为5           |
| `0x1800:01` | TPDO1 COB-ID                   | `UNSIGNED32`，固定                 |
| `0x1800:02` | TPDO1 Transmission Type        | `UNSIGNED8`，固定，值为255         |
| `0x1800:03` | TPDO1 抑制时间                 | `UNSIGNED16`，固定为0              |
| `0x1800:05` | TPDO1 事件周期                 | `UNSIGNED16`，Pre-operational 可写 |

TPDO1 是：

```
从站 → 主站
```

当前 Node-ID 为1时：

```
TPDO1 CAN-ID = 0x180 + 1 = 0x181
```

其中：

```
0x1800:03 → 两次TPDO1发送之间的最小间隔
0x1800:05 → TPDO1的事件周期
```

当前抑制时间固定为0；事件周期默认也是0，需要时可以在 Pre-operational 状态配置。

子索引4保留，因此没有：

```
0x1800:04
```

------

### 9. TPDO2 通信参数

| 条目        | 含义                           | 类型／权限                         |
| ----------- | ------------------------------ | ---------------------------------- |
| `0x1801:00` | TPDO2 参数子项数量／最高子索引 | `UNSIGNED8`，固定，值为5           |
| `0x1801:01` | TPDO2 COB-ID                   | `UNSIGNED32`，固定                 |
| `0x1801:02` | TPDO2 Transmission Type        | `UNSIGNED8`，固定，值为255         |
| `0x1801:03` | TPDO2 抑制时间                 | `UNSIGNED16`，固定为0              |
| `0x1801:05` | TPDO2 事件周期                 | `UNSIGNED16`，Pre-operational 可写 |

Node-ID 为1时：

```
TPDO2 CAN-ID = 0x280 + 1 = 0x281
```

TPDO2 用来发送两路 AI：

```
TPDO2
├── AI1：0x6401:01
└── AI2：0x6401:02
```

当前默认事件周期是：

```
0
```

以后如果要每100 ms发送一次，可以在预运行状态写入：

```
0x1801:05 = 100
```

------



### 10. TPDO1 映射参数

| 条目        | 含义           | 类型／权限                            |
| ----------- | -------------- | ------------------------------------- |
| `0x1A00:00` | TPDO1 映射数量 | `UNSIGNED8`，固定，值为1              |
| `0x1A00:01` | 第一个映射对象 | `UNSIGNED32`，固定，值为 `0x60000108` |

拆开：

```
0x6000 → Index
0x01   → Sub-index
0x08   → 8 bit，也就是1字节
```

所以：

```
TPDO1 的数据 → 来自 0x6000:01，也就是四路 DI 状态
```

------



### 11. TPDO2 映射参数

| 条目        | 含义           | 类型／权限                            |
| ----------- | -------------- | ------------------------------------- |
| `0x1A01:00` | TPDO2 映射数量 | `UNSIGNED8`，固定，值为2              |
| `0x1A01:01` | 第一个映射对象 | `UNSIGNED32`，固定，值为 `0x64010110` |
| `0x1A01:02` | 第二个映射对象 | `UNSIGNED32`，固定，值为 `0x64010210` |

拆开：

```c
0x64010110
├── 0x6401 → Index
├── 0x01   → Sub-index
└── 0x10   → 16 bit，也就是2字节
0x64010210
├── 0x6401 → Index
├── 0x02   → Sub-index
└── 0x10   → 16 bit，也就是2字节
```

因此 TPDO2 的数据长度是：

```c
AI1：2字节
AI2：2字节
总长度：4字节
```

------



### 12. 模拟量变化触发开关

| 条目        | 含义                   | 类型／权限               |
| ----------- | ---------------------- | ------------------------ |
| `0x6423:00` | 模拟量全局变化触发开关 | `BOOLEAN`，可读写，默认0 |

它的作用是：

```
0 → 不因为AI变化立即触发TPDO
1 → 允许AI变化触发TPDO
```

它不是：

```
不是 ADC 开关
不是 STM32 硬件中断开关
不是 TPDO2 事件周期
```

它是 CANopen 层面的**模拟量变化触发配置**，真正使用它发送 PDO，要等阶段 6。



## 最后按功能重新归类

你可以把 36 个条目分成五组：

```c
一、设备身份和状态	//设备身份和状态：8 个
    0x1000
    0x1001
    0x1017
    0x1018:00～04

二、真实 I/O 数据		//真实 I/O 数据：  7 个
    0x6000:00～01
    0x6200:00～01
    0x6401:00～02

三、RPDO 配置		//RPDO 配置：      5 个
    0x1400:00～02
    0x1600:00～01

四、TPDO 配置				//TPDO 配置：      15 个
    0x1800:00、01、02、03、05
    0x1801:00、01、02、03、05
    0x1A00:00～01
    0x1A01:00～02

五、模拟量触发配置			//AI 触发配置：    1 个
    0x6423:00
 //总计：            36 个
```

所以最初列出的几个是“**应用数据对象**”，而完整的 36 个条目还包括了**描述这些数据如何通信、如何映射、如何配置和如何识别设备的对象**。
